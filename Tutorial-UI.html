🚆 Why Ontologies Are Useful in Digital Twin Creation

Digital Twins represent real-world entities digitally. To keep those twins structured, discoverable, and interconnected, an ontology ensures:

  • Consistency: Every Station must have a stationId
  • Validation: Detect a Train claiming to be on a non-existent Line
  • Reasoning: Find all trains arriving at stations with accessibility features
  • Visualisation: Map stations based on latitude/longitude

🏗️ How to Develop an Ontology From Assets and Relationships

Building an ontology is a structured, iterative process. You start with an understanding of what exists in the real system and how these things interact. From this, you create a formal digital representation using a language like DTDL.

This section explains how to go from real-world understanding → structured ontology.

1. Identify the Real-World Domain

The first step in creating an ontology is understanding the domain you want to model.

Example domain: London Railway System

Key questions:

  • What physical objects exist?
  • What logical concepts exist?
  • What data is generated?
  • What entities interact?
  • What does the system need to represent digitally?

From these questions, the domain assets emerge.

2. Identify the Core Asset Types

Assets are the noun concepts of the system.

In a transit system, typical assets include:
  • ✓ Stations
  • ✓ Trains
  • ✓ Lines
  • ✓ Routes
  • ✓ Operators
  • ✓ Accessibility features

How to determine whether something should be an asset:

  • Does it exist independently in the real world?
  • Does it have data associated with it?
  • Can it appear more than once?
  • Will it need to connect to other entities?
3. Define Properties for Each Asset

Every asset needs properties describing its characteristics.

Station properties:
  • • name
  • • stationId
  • • latitude
  • • longitude

Why these? Required to label, index, and place stations on maps.

Train properties:
  • • timestamp
  • • expectedArrival
  • • vehicleId
  • • secondsToNextStop

Why these? Telemetry feeds into dashboards and analytics.

4. Identify Relationships Between Assets

Relationships turn isolated assets into a connected graph, which is essential for digital twins.

How to choose relationships:

  • Which assets depend on others?
  • Which assets group or organise other assets?
  • What does the system need to query in real-world terms?
  • What is the flow of data or movement?

Station → servedByLine → Line:

A station belongs to one or more transit lines

Example query enabled:

  • “Show all stations on the Red Line.”

Route → onLine → Line:

A route is part of exactly one line.

This mirrors operational rules:

  • lines usually have multiple routes but each route belongs to one line.

Train → servesRoute → Route:

The train follows a specific path composed of an ordered sequence of stations.

This allows:

  • Real-time train tracking
  • Prediction of next stations

Station → hasAccessibilityFeature → AccessibilityFeature:

Highlight stations with accessibility features

A station offers accessibility options like elevators.

  • Accessibility planning
  • Compliance reporting
  • Enhanced journey planning
5. Relationship Cardinality and Direction
Even though DTDL does not explicitly define cardinality, it is important in ontology design.
For example:
  • • A Station can be served by multiple Lines
  • • A Route belongs to one Line
  • • A Train serves one Route at a time
  • • A TransportOperator can operate many Lines

Why? Documenting intended cardinality helps validate real data and avoid incorrect connections

6. Design the Graph Structure
Once assets and relationships are defined, the ontology can be viewed as a graph:
For example:
  • Nodes = assets
  • Edges = relationships
A well-designed graph should reflect:
For example:
  • • Hierarchy (e.g., Operator → Line → Route)
  • • Network structure (e.g., Station ↔ Station via Route)
  • • Movement (Trains moving along Routes)
  • • Categories and grouping (Accessibility features)

This graph structure enables:

  • Navigation algorithms
  • Query optimisation
  • Pathfinding
  • Visualisation tools
7. Visualising the Ontology (during development)

Before implementing, visualisation helps ensure the ontology is correct and complete.

Useful diagrams:

1. Asset hierarchy diagram

  • Shows all asset types

2. Relationship network

  • Repository-style diagram showing edges between entities.
  • Helpful for verifying directions and completeness.

3. Sequence diagrams (for dynamic assets like trains)

  • Show how entities interact over time.

4. Map visualisation prototype

  • Use station coordinates to validate connectivity.
Visualisation early in development helps catch:
  • • Missing relationships
  • • Misinterpreted concepts
  • • Cycles where none should exist
  • • Redundant asset types
8. Validate the Ontology Design

Before implementing, validate the model:

Structural validation

  • Does every relationship point to a real asset?
  • Are all property types legal in DTDL?
  • Are DTMI identifiers correct?

Semantic validation

  • Does the ontology reflect the real system?
  • Are all cardinalities respected?
  • Is there redundancy or ambiguity?

Semantic validation

  • Does the ontology reflect the real system?
  • Are all cardinalities respected?
  • Is there redundancy or ambiguity?

Graph validation

  • Simulate a few real-world cases:
  • Add example Station twins

Ontologiesevolve.

Once real data enters the system, you may discover:
  • • New properties are needed
  • • Better relationship patterns
  • • Additional asset types
  • • More constraints

A good ontology handles extension without breaking existing structure.

Storing Real-Time and Historical Data

Digital Twins must support real-time state AND historical analysis.

Common tools used for data storage include InfluxDB, TimescaleDB, and Azure Data Explorer.

Two main storage patterns:

1

Graph storage

  • Stores the digital twin entities and relationships
  • Optimised for querying structure (“which trains serve Route X?”)
2

Time-series storage

  • Stores changing telemetry
  • Optimised for historical analytics (“delays over last 24 hours”)

Key considerations:

  • retention policies
  • indexing
  • handling out-of-order data
  • writing frequency
  • tagging strategy

✔ Data validation ensures the twin does not ingest incorrect or inconsistent information.

Key validation types:

1

Schema validation

  • property types
  • required fields
  • cardinality
2

Semantic Validation

  • IDs must map to existing assets
  • relationships must be valid
  • values must be within expected ranges
3

Temporal validation

  • timestamps must be ordered
  • prediction times must be in the future
  • stale data should be discarded
4

Business logic validation

  • measurement cannot be negative
  • vehicle direction must match route
  • entity must belong to the correct line

In the London Underground Example

TfL API issues can include:

  • missing timeToStation
  • inconsistent timestamps
  • duplicate entries
  • trains appearing outside of known routes

Validation steps:

1

Schema Rules

  • vehicleId, lineId, naptanId must be strings
  • timeToStation must be ≥ 0
  • timestamps must be ISO 8601
2

Semantic Rules

  • naptanId must match a Station twin
  • lineId must match a Line twin
  • vehicleId must be stable over time
3

Route Validation

  • Next station must be in the known station sequence
  • Order must align with inferred direction
Once data passes validation, it is safe to:
  • ✔ update Train entities in the digital twin
  • ✔ update Station status
  • ✔ compute performance metrics
  • ✔ trigger alerts

In the London Underground Example

1️⃣ Find all stations served by a specific line

                                
                                    cypher

                                    CREATE (a:Person {name: 'Alice'})
                                    CREATE (b:Person {name: 'Bob'})
                                    CREATE (a)-[:KNOWS]->(b)
                                    RETURN a, b;

2️⃣ Show the route sequence for a given Route

                                
                                    cypher 

                                    MATCH (r:Route {routeId: "central-eastbound"})
                                    RETURN r.stationSequence;

3️⃣ Find all trains currently associated with a specific route

                                
                                    cypher

                                    MATCH (t:Train)-[:servesRoute]->(r:Route {routeId: "central-eastbound"})
                                    RETURN t.vehicleId, t.expectedArrival, t.nextStationName;

4️⃣ Validate that all stations have a line relationship

                                
                                    cypher

                                    MATCH (s:Station)
                                    WHERE NOT (s)-[:servedByLine]->(:Line)
                                    RETURN s;

Time-series queries analyse system behaviour over time:

  • Trends
  • Performance
  • Delay patterns
  • Movement
  • Predictions vs actuals

These help validate telemetry and support analytics.

In the London Underground Example

1️⃣ Get the last known update for each train

                                
                                    flux 

                                    from(bucket: "underground")
                                        |> range(start: -10m)
                                        |> filter(fn: (r) => r._measurement == "train_status")
                                        |> group(columns: ["vehicleId"])
                                        |> last()

2️⃣ Plot delays for a specific line over time

                                
                                    flux 

                                    from(bucket: "underground")
                                        |> range(start: -2h)
                                        |> filter(fn: (r) => r.lineId == "central")
                                        |> filter(fn: (r) => r._field == "secondsToNextStop")

3️⃣ Get busiest stations (most train arrivals)

                                
                                    flux 

                                    from(bucket: "underground")
                                        |> range(start: -24h)
                                        |> filter(fn: (r) => r._field == "secondsToNextStop")
                                        |> aggregateWindow(every: 5m, fn: count)
                                        |> group(columns: ["nextStationId"])
                                    |> sum(column: "_value")

4️⃣ Compare predicted vs actual arrival times

(Assuming you store actual arrival events)

                                
                                    flux

                                    // Predicted
                                    predicted = from(bucket: "underground")
                                    |> range(start: -1h)
                                    |> filter(fn: (r) => r._field == "expectedArrival")

                                    // Actual
                                    actual = from(bucket: "underground")
                                    |> range(start: -1h)
                                    |> filter(fn: (r) => r._field == "actualArrival")

                                    join(
                                    tables: {predicted: predicted, actual: actual},
                                    on: ["vehicleId", "nextStationId"]
                                    )

2️⃣ Calculate the interpolated position between two stations

                                
                                    python

                                    def interpolate_position(lat1, lon1, lat2, lon2, progress):
                                        return (
                                            lat1 + (lat2 - lat1) * progress,
                                            lon1 + (lon2 - lon1) * progress
                                    )

3️⃣ Find the train closest to a given station

                                
                                    python (Using SQL)

                                    MATCH (t:Train)-[:servesRoute]->(r:Route),
                                            (s:Station {stationId: $target})
                                    RETURN t.vehicleId, t.nextStationId, t.secondsToNextStop
                                    ORDER BY t.secondsToNextStop ASC
                                    LIMIT 1;

4️⃣ Get trains running on a specific line and their next stations

                                
                                    python (Using SQL)

                                    MATCH (t:Train)
                                    WHERE t.lineId = "central"
                                    RETURN t.vehicleId, t.nextStationName, t.secondsToNextStop;

In the London Underground Example

1️⃣ Stations without coordinates

                            
                                cypher

                                MATCH (s:Station)
                                WHERE s.latitude IS NULL OR s.longitude IS NULL
                                RETURN s.stationId, s.name;

2️⃣ Trains linked to a non-existent line

                            
                                cypher

                                MATCH (t:Train)
                                WHERE NOT (t)-[:servesRoute]->(:Route)

3️⃣ Routes with missing stations

                            
                                cypher

                                MATCH (r:Route)
                                UNWIND r.stationSequence AS stationId
                                OPTIONAL MATCH (s:Station {stationId: stationId})
                                WHERE s IS NULL
                                RETURN r.routeId, stationId;

                                    from(bucket: "underground")
